# Milena TUR package contract

`tur/milena/build.sh` packages only the canonical `46Neon/Milena` release tarball. TUR builds and distributes; it does not contain or add a parser, interpreter, runtime, semantic wrapper, Android backend, generated source, or external tool. The executable therefore remains the upstream lexer -> parser -> AST -> semantic -> runtime -> MilenaTable implementation. Experimental compiler/IR/VM/GC modules and Mano are never copied into this repository or the package.

## Release and source guards

For every update, `TERMUX_PKG_VERSION`, the `v<version>` tag in `TERMUX_PKG_SRCURL`, and `TERMUX_PKG_SHA256` must be updated together. The recipe rejects a missing Makefile/license/README, a non-`milena` Make target, a mismatched `MILENA_VERSION`, missing canonical lexer/parser/AST/semantic/runtime/table sources, and failures of the upstream source-manifest and experimental-isolation checks. `TERMUX_PKG_LICENSE_FILE=LICENSE` and the explicit install step preserve the license in the normal TUR documentation payload.

## Build flags and tests

The build invokes upstream `make TERMUX=1` with TUR's compiler and job count. It deliberately does not assign `CFLAGS` or `LDFLAGS`: Milena's `TERMUX=1` Makefile defaults retain `-Oz`, function/data sections, and `--gc-sections`, while TUR-provided flags remain authoritative instead of being overwritten. No Debian/glibc flags are introduced.

`termux_step_make_test` is only a hook, not proof that a TUR workflow called it. TUR/build-package versions that do not schedule that hook must run the test explicitly in the extracted source tree, separately from packaging:

```sh
./build-package.sh -I -C milena
make TERMUX=1 CC="${CC:-clang}" test
./milena --version
```

The second and third commands are a source-tree test/smoke phase; their test executables are not installed. A package build without that explicit phase must be reported as build-only, not test-passed.

## Isolated staging, ELF audit, and payload

Post-install checks use `${TERMUX_PKG_MASSAGEDIR}${TERMUX_PREFIX}` only. They never inspect or mutate the host/device `$TERMUX_PREFIX`, so unrelated installed packages cannot satisfy the contract. The staged payload is exactly:

- `bin/milena`
- `share/doc/milena/README.md`
- `share/doc/milena/LICENSE`

Normal TUR control metadata is generated by TUR and is not source payload. Tests, source files, scripts, Makefiles, compilers, objects, headers, examples, Mano, and experimental modules must not be copied into the package. If `llvm-readelf` or `readelf` is available, the recipe audits the staged file as ELF and rejects unexpected `DT_NEEDED` libraries; absence of the optional inspection tool is recorded as an audit limitation rather than replaced with a fake Android claim.

## Cross-build versus real-device evidence

Cross-build CI validates the recipe, source checksum, Android/Bionic compiler (`__ANDROID__`), C17 compilation, staged metadata/payload, and (when available) ELF/`DT_NEEDED`. It does not prove installation or behavior on hardware. The supported target matrix must be taken from the active TUR workflow; the recipe does not claim architectures that were not built.

A separate real-device test is required for each claimed ABI. It must record observed values, never inferred values:

```sh
uname -o -m
getprop ro.product.cpu.abi
command -v pkg make clang
clang --version
pkg update
pkg install tur-repo
pkg install milena
milena --version
pkg upgrade
pkg remove milena
```

Android/Bionic and `aarch64` are an expected target example, not evidence of publication or success. Until a labeled physical Termux device/runner executes the lifecycle, device status is **pending**. QEMU, an emulator, a container, and host Linux are not physical-device evidence. This document does not claim that TUR publishes `milena`, that `tur-repo` is configured, or that any architecture has passed.
